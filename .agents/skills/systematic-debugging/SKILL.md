# 系统化排查

先把故障缩小到可区分的原因，再在故障发生的入口修复。按 [架构文档](../../../docs/architecture.md) 确认问题涉及 `app`、`game-core` 还是数据和存档交界处。

## 记录与复现

1. 从实际入口记录预期、结果、操作顺序和第一处异常。构建故障保留失败任务、首条错误和退出状态。手机问题记录系统版本、横屏比例和重启前后的操作。
2. 选择能复现故障的最小路径。纯规则问题用当前状态、玩家动作、配置和随机种子在 JVM 重放。触控、窗口或存档问题用 Android 运行验证，采用能复现问题的虚构存档。
3. 核对正常路径或最近一次可用结果。沿输入动作、规则结果、存档提交、界面呈现的顺序找出首处分歧。

## 验证假设

- 每轮用一次定向检查验证一个可证伪的假设。假设被推翻时撤回对应试验改动，用新证据缩小范围；连续试验没有缩小范围时重新核对输入、模块归属和复现条件。
- 战斗结果异常时对比相同种子和动作序列。奖励异常时检查结算标记与潜能是否一起提交。重启问题对比最后一次成功提交的快照与实际恢复时读取的版本。
- 横屏问题先确认窗口安全区、按钮实际触达范围和滚动区域，再检查触控是否被分发成了正确的玩家动作。

## 修复与收口

修复后重跑同一个最小复现。现有检查捕捉不到本次回归时，补一项能证明行为的针对性检查，再按改动范围执行 [完成前验证](../verification-before-completion/SKILL.md)。

以 [README.md](../../../README.md) 登记的实际工程入口为准。处于文档阶段时，核对约定、路径和引用；需要工程或设备才能确认的部分记录所缺条件。
